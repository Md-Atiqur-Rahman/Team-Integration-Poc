Teams Connection Internals

1

First-time login — Himel

POST /api/demo/login

  1. Himel submits himel@demo.autom / Demo@123 on the demo login screen. This posts to POST /api/demo/login — DemoAuthController.Login.
  2. The controller calls DemoAuthService.ValidateCredentialsAsync. Before checking anything, it re-upserts all five seed users (Himel, Ratan, Sabbir, Anik, Jim) into the DemoUsers collection — idempotent, harmless if they already exist, and self-healing if the collection was ever wiped.
  3. It then does a plain Find(u => u.Email == email) against DemoUsers and compares user.Password == password as plain text. No hashing, no JWT — this is demo-only scaffolding, deliberately.
  4. On a match, the controller returns 200 with { displayName, organizationId, projectId, applicationId } — for Himel that's { "Himel", "IGB2B", "Ecohub", "EcohubApp" }. Nothing is written for the login itself beyond the seeding upsert.
  5. The Angular DemoAuthFlowStore holds that response and shows Choose Organization (one match: IGB2B), then Choose Project (one match: Ecohub). Choosing the project does a full page navigation — not an API call — to ?organizationId=IGB2B&projectId=Ecohub&applicationId=EcohubApp&displayName=Himel.
  6. On reload, app.ts sees organizationId in the URL and renders the dashboard instead of the login screen. Everything downstream reads host context from these URL query params, not from any stored session.
2

First-time Teams Connect

GET /api/auth/connect → Entra sign-in → GET /api/auth/connect-complete

  1. The dashboard's first call is GET /api/auth/connection-status?organizationId=IGB2B. AuthController.GetConnectionStatus reads OrganizationTeamsConnections filtered by organizationId alone — nothing there yet, so it returns { isConnected: false, connectionStatus: "none" }. The UI shows "Not Connected" + a Connect button.
  2. Himel clicks Connect. The browser does a full navigation to GET /api/auth/connect?returnUrl=<current dashboard URL>. AuthController.Connect validates the return URL's origin against Frontend:BaseUrl, pulls organizationId=IGB2B back out of it, and builds a redirect target of its own: /api/auth/connect-complete?organizationId=IGB2B&returnUrl=....
  3. It calls ASP.NET Core's Challenge(), which 302s the browser to Microsoft's real sign-in page (login.microsoftonline.com/organizations/oauth2/v2.0/authorize) requesting the three Graph scopes plus openid profile offline_access.
  4. Himel signs in as Atiqur.Himel@selisegroup.com and consents. Microsoft redirects back with an authorization code to POST /api/auth/callback (the OIDC callback path, handled entirely by the Microsoft.Identity.Web middleware — no controller code of ours runs here).
  5. The middleware exchanges that code for an access token, refresh token, and ID token by calling Microsoft's token endpoint directly (server-to-server, via MSAL). This is the first real token acquisition — MSAL saves the whole result into the distributed cache (Redis), encrypted via Data Protection.
  6. ASP.NET Core also issues its own sign-in cookie for Himel's browser at this point — separate from the Graph tokens, it just proves he completed sign-in for this app.
  7. The browser is redirected on to GET /api/auth/connect-complete, which requires that fresh cookie ([Authorize]). It reads the oid/tid claims and email off User, then connectionRepository.UpsertAsync(...) writes one document to OrganizationTeamsConnections: { organizationId: "IGB2B", tenantId, userObjectId, connectedAsEmail: "Atiqur.Himel@selisegroup.com", connectionStatus: "active" }.
  8. It redirects back to the original dashboard URL. The dashboard reloads, calls connection-status again — now active — and shows "Connected as Atiqur.Himel@selisegroup.com". Because status is active, it also fires GET /api/teams and GET /api/teams/configuration in parallel.
  9. GET /api/teams resolves a GraphIdentity from that same Mongo document, builds a synthetic identity out of it, and calls ITokenAcquisition.GetAccessTokenForUserAsync(...) — MSAL finds the token it just cached in Redis (no new Microsoft round trip) and the API calls GET https://graph.microsoft.com/v1.0/me/joinedTeams for real.
3

Configure a channel, then send

GET /api/teams/{id}/channels · PUT /api/teams/configuration · POST /api/teams/messages

  1. Picking a Team in the dropdown fires GET /api/teams/{teamId}/channels?organizationId=IGB2B. Same identity resolution as before (Mongo → GraphIdentity → cached Redis token), then a real, paginated Graph call: GET /teams/{id}/channels?$select=id,displayName,....
  2. Saving fires PUT /api/teams/configuration with {organizationId, projectId, applicationId, teamId, channelId}. TeamsConfigurationService.SaveAsync re-reads OrganizationTeamsConnections for the org, then revalidates both choices against Graph again (fresh GetTeamsAsync + GetChannelsAsync calls) before saving anything.
  3. Once both match, it upserts one document into TeamsConfigurations, keyed by the unique compound index {organizationId, projectId, applicationId}: {teamId, teamName, channelId, channelName, tenantId, userObjectId, connectionStatus:"active"}. tenantId/userObjectId here come from the org connection, not from whoever clicked Save.
  4. The dashboard flips to the Send Message view. Typing a message and sending fires POST /api/teams/messages?organizationId=...&projectId=...&applicationId=... with {content}.
  5. TeamsMessagesController first reads the saved config back from TeamsConfigurations (404 if none), then hands it to TeamsMessageService.SendAsync.
  6. That service reads OrganizationTeamsConnections again (not the config's own stored tenant/user fields) to get the current GraphIdentity, re-checks the team still exists, re-checks the channel still exists (either miss → 409 stale_configuration), then calls Graph for real: POST /teams/{teamId}/channels/{channelId}/messages.
  7. Graph answers 201 Created with the message id, timestamp, and webUrl — the API forwards all three back to the browser as 201, and the UI shows "Message sent · View in Teams".

Ratan logs in — same org, zero OAuth

Same org/project as Himel: IGB2B / Ecohub / EcohubApp

The one field that makes this work: OrganizationTeamsConnections is keyed uniquely by organizationId alone — not by which user is asking. Ratan's request never carries his own identity into any Teams/Graph lookup; TeamsController, TeamsConfigurationController, and TeamsMessagesController are all [AllowAnonymous] and never read User at all. "Ratan" only ever exists as display text in the page header.
  1. Ratan logs in with ratan@demo.autom. The seed data gives him the identical triple Himel has: {IGB2B, Ecohub, EcohubApp}. He lands on the exact same dashboard URL shape Himel used.
  2. GET /api/auth/connection-status?organizationId=IGB2B runs the same Mongo query as before, filtered only by organizationId — it finds Himel's document, because there's only one document per organization, period. Ratan's browser has never done a Microsoft sign-in and holds no Entra cookie whatsoever; that's never checked.
  3. GET /api/teams?organizationId=IGB2B: TeamsController.ResolveIdentityAsync reads that same document and builds a GraphIdentity out of Himel's tenantId/userObjectId. The token pulled from Redis is Himel's cached token. Graph is called as Himel.
  4. GET /api/teams/configuration?organizationId=IGB2B&projectId=Ecohub&applicationId=EcohubApp: because Ratan's project triple is byte-for-byte identical to Himel's, this is the exact same document lookup in TeamsConfigurations — it returns the "Autom Product Team / Incoming Webhook" config Himel already saved. View mode goes straight to Send Message.
  5. Sending as Ratan runs the identical TeamsMessageService.SendAsync path from Section 3 — it resolves GraphIdentity from Mongo, not from Ratan, and posts to Graph as Himel's account.

Sabbir logs in — connected, but unconfigured

Same org as Himel, different project: IGB2B / Ecap / EcapApp

  1. Sabbir's org-connection check is identical to Ratan's: connection-status?organizationId=IGB2B still finds Himel's document, because the org-level connection has no idea what "project" even means — it's one flag per organization. Sabbir's card shows "Connected as Atiqur.Himel@selisegroup.com" too.
  2. Because status came back active, the store also fires GET /api/teams/configuration?organizationId=IGB2B&projectId=Ecap&applicationId=EcapApp — a completely separate lookup, keyed by the full three-part compound index.
  3. That triple has never been saved by anyone. TeamsConfigurations.find(...) returns nothing, the endpoint answers 404 configuration_not_found, and configurationLoadState becomes 'none'.
  4. Two independent booleans decide the screen: isConnected (org-level, true) picks whether the Connection card and the Configuration card render at all; configurationLoadState/viewMode (project-level, 'configure') picks which card body shows. Sabbir gets the Team/Channel picker, pre-populated from Himel's Graph identity, with "No Teams configuration is saved for this application yet."
  5. Saving from here writes a brand-new TeamsConfigurations document for {IGB2B, Ecap, EcapApp}, independent of Himel's {IGB2B, Ecohub, EcohubApp} one — same organization, two separate saved destinations.

Jim logs in — a different organization entirely

SwissLife / SwissLifeProject / SwissLifeApp

  1. Jim's seed row carries organizationId: "SwissLife" — nothing shared with IGB2B.
  2. GET /api/auth/connection-status?organizationId=SwissLife filters OrganizationTeamsConnections by that exact string. No document has ever been written with organizationId: "SwissLife", so the query returns nothing and the endpoint answers {isConnected:false, connectionStatus:"none"}.
  3. The dashboard shows "Not Connected" + a Connect button — the same very-first state Himel started from. Because status isn't active, the store never calls GET /api/teams or GET /api/teams/configuration at all, and the Configuration card doesn't render.
  4. If Jim clicks Connect, it's a full fresh OAuth round trip through his own Microsoft account, landing on ConnectComplete, which upserts a new, separate OrganizationTeamsConnections document keyed organizationId: "SwissLife".
  5. The isolation mechanism is nothing more exotic than that string plus the unique index on it — every one of these endpoints always filters by the organizationId that arrived in the caller's own query string, and never looks at any other organization's document.

Token lifecycle & the reconnect path

Where the access token is used

Only inside TeamsGraphService.SendAsync — it's attached as Authorization: Bearer <token> on every real Graph call (GET me/joinedTeams, GET teams/{id}/channels, POST .../messages). No controller or service ever sees the raw token; it's fetched fresh from ITokenAcquisition.GetAccessTokenForUserAsync(...) right before each call.

Where the refresh token is used

Nowhere in this codebase directly — it's never read, never passed around. It lives inside the encrypted token-cache blob that Microsoft.Identity.Web writes to Redis, and only MSAL's own internals ever touch it.

Redis, step by step

  • Write: happens automatically inside Microsoft.Identity.Web, at the end of the OIDC sign-in (the code-for-tokens exchange in Section 2) and again any time MSAL silently renews a token.
  • Read: happens on every single GetAccessTokenForUserAsync(...) call — MSAL's AcquireTokenSilent looks for a cached, still-valid access token under the account key {uid}.{utid} before doing anything else over the network.
  • Every cache entry is encrypted (ASP.NET Core Data Protection, Encrypt = true) before it's written. No raw token ever appears in MongoDB — neither OrganizationTeamsConnections nor TeamsConfigurations has a token field, only identifiers (tenantId, userObjectId).

Where MSAL actually gets invoked

  1. Program.cs wires it up once at startup: AddMicrosoftIdentityWebApp(...).EnableTokenAcquisitionToCallDownstreamApi(...).AddDistributedTokenCaches().
  2. During POST /api/auth/callback — the framework's own OIDC handler runs MSAL's AcquireTokenByAuthorizationCode, entirely outside our controller code.
  3. Inside every TeamsGraphService.SendAsync call — GetAccessTokenForUserAsync(...), MSAL's AcquireTokenSilent path.
Unconfirmed — needs verification Whether an expired access token gets silently renewed using the refresh token, transparently inside the same GetAccessTokenForUserAsync call, is standard documented MSAL behavior — but it was not directly observed in this session. Every successful call we watched was a straight cache hit on a token acquired minutes earlier, not a renewal of an expired one. If asked live: describe it as "MSAL is supposed to handle this automatically," not as something this team has watched happen.

When the refresh token itself is dead — the needsReconnect path

  1. Any Graph call throws MicrosoftIdentityWebChallengeUserException when MSAL can't silently recover — refresh token expired, consent revoked, password changed, a Conditional Access policy demands a fresh interactive sign-in. TeamsGraphService maps that to TeamsGraphException(401, ...).
  2. Whichever service call was in flight catches that specific 401 and calls OrganizationTeamsConnectionRepository.MarkNeedsReconnectAsync(organizationId, "reauthentication_required", ...).
  3. That writes to the same OrganizationTeamsConnections document: connectionStatus → "needsReconnect", plus a failure code and timestamp. Because it's one document per org, this instantly affects every project and every user in that organization — not just whoever triggered it.
  4. The exception is rethrown and caught by the global TeamsGraphExceptionHandler middleware, which answers 401 with { code: "reauthentication_required" } in the body.
  5. The frontend's global reauthenticationInterceptor watches every response; on this exact code it calls store.markNeedsReconnect(), flipping the UI immediately without another round trip.
  6. The connection card shows "Teams connection needs reconnecting. Notifications for this application are paused." with a Reconnect button. Anyone else opening the dashboard afterward sees the same thing, straight from Mongo.
  7. Reconnect runs the exact same flow as Section 2, step 2 onward — a fresh OAuth round trip, ending in ConnectComplete upserting the same document back to connectionStatus: "active" with every failure field cleared. The whole organization is healthy again the moment that one document is overwritten.
